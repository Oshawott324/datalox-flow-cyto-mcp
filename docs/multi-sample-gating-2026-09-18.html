Multi-Sample Rendering & Pooled Gate Suggestion

Three capabilities: multi-sample inspection renders, a new dedicated main-cell gate tool, and pooled event sampling so morphology gates generalise across the cohort rather than overfit a single file.

Overview

Current single-sample gate proposal risks overfitting coordinates to one sample's distribution. When treatment groups shift morphology or fluorescence baselines, gates drawn from one sample misclassify events in others.

Three coordinated capabilities address this:

  • Inspection — render multiple samples side-by-side with matched axes so the agent detects distribution shifts, debris differences, or compensation artefacts before committing coordinates.
  • Robust fitting — pooled event sampling across eligible samples ensures gate coordinates sit at the population centroid of the cohort. One low-event sample is excluded, not allowed to shrink the pool for all others.
  • Dedicated main-cell tool — suggest_main_cell_gate covers the FSC/SSC debris-exclusion step that suggest_singlet_gate does not. The three-level hierarchy — main cell, singlet, apoptosis quadrants — now has a dedicated suggest tool at each level.

Physical file concatenation is not a primitive. Event pooling happens in-memory; no new FCS object is created or persisted.

Feature 1 — Multi-sample render_plot / render_plot_image

Extend both render tools with optional sample_ids and mode. Single-sample calls are unchanged.

New parameters

ParameterTypeDefaultDescription
sample_ids string[] — When provided, renders multiple samples. Mutually exclusive with singular sample_id; server validates and returns an error if both are present.
mode "small_multiples" | "overlay" "small_multiples" Rendering layout. Only valid when sample_ids is provided. Ignored on single-sample calls.

small_multiples mode (default)

N separate density maps in the same coordinate space. Per-sample identity is preserved, making outlier detection unambiguous. This is the correct default for inspection.

  • Axis bounds computed as the union of all sample extents, then shared. Existing explicit bounds parameter overrides the computed union.
  • Each plot entry contains sampleId, eventCount, and the same bins/contour format as a single-sample response.
  • eventCountPerSample at the top level lets the agent flag anomalously small samples before gating.
// render_plot response — small_multiples
{
  mode: "small_multiples",
  sharedBounds: { xMin: 0, xMax: 262143, yMin: 0, yMax: 262143 },
  eventCountPerSample: { "group_1": 16942, "group_2": 21289 },
  plots: [
    { sampleId: "group_1", eventCount: 16942, bins: [ /* same as single-sample */ ] },
    // … one entry per sample_id, in input order
  ]
}

overlay mode

All sample events projected into one 2D density grid. Lower priority than small_multiples; implement after small_multiples is stable.

// render_plot response — overlay
{
  mode: "overlay",
  eventCountPerSample: { "group_1": 16942, "group_2": 21289 },
  bins: [ /* merged bins, same schema as single-sample */ ]
}
Agent workflow

Call render_plot_image(sample_ids=[…], mode="small_multiples") before proposing any gate geometry. Inspect for FSC/SSC cloud position differences, channel baseline shifts, or anomalously low event counts. Proceed to gate suggestion only after confirming samples are comparable.

Feature 2 — Pooled event sampling (shared contract)

This parameter contract applies to suggest_main_cell_gate and suggest_singlet_gate (and any future morphology gate tool). When sample_ids is provided, events are drawn equally from each eligible sample. Samples below min_events_for_pooling are excluded — not used to shrink the pool for the others.

New parameters (all morphology suggest tools)

ParameterTypeDefaultDescription
sample_ids string[] — Samples to pool. Replaces singular sample_id. All IDs must exist in the workspace.
max_events_per_sample number 5000 Upper bound on events drawn per eligible sample. Effective count further capped by the smallest eligible sample. Does not affect excluded samples.
min_events_for_pooling number 500 Minimum eligible event count to include a sample in pooling. Samples below this are excluded and reported in excludedSampleIds. They still appear in inspection renders and receive counts after gate propagation.
seed number 42 Random seed for reproducible subsampling. Same workspace + seed + parameters → identical pooled gate coordinates.
Eligible event count

For root-level gates (no parent), eligible count is raw FCS $TOT. For child gates, eligible count is events surviving the parent gate for that sample. A sample with 50,000 total events but only 4,200 inside the main-cell gate contributes 4,200 toward min_events_for_pooling and the subsample cap.

Pool construction algorithm

const cap = input.max_events_per_sample ?? 5000;
const minForPooling = input.min_events_for_pooling ?? 500;

// eligible count: events after parent gate filter, or $TOT for root-level
const eligibleCounts = await readEligibleCounts(sampleIds, parentGateId);

const included = sampleIds.filter(id => eligibleCounts.get(id) ?? 0) >= minForPooling);
const excluded = sampleIds.filter(id => eligibleCounts.get(id) ?? 0) < minForPooling);

// guard: must have at least 2 eligible samples to pool
if (included.length === 0)
  throw FlowcytoError("insufficient_events_for_pooling", ...);

const minCount = Math.min(...included.map(id => eligibleCounts.get(id)!));
const effectiveN = Math.min(cap, minCount);

// null when cap is the binding constraint (minCount >= cap)
const limitedBySampleId =
  minCount < cap ? included.find(id => eligibleCounts.get(id) === minCount)!
             : null;

const pooled = included.flatMap(id => sampleRandomSubset(id, effectiveN, seed));

Diagnostics & error cases

Normal response

{
  gate: { /* polygon — same shape as single-sample */ },
  poolingDiagnostics: {
    requestedMaxEventsPerSample: 5000,
    minEventsForPooling: 500,
    effectiveEventsPerSample: 3241,
    limitedBySampleId: "group_5",  // null when cap was binding
    includedSampleIds: ["group_1", "group_2", "group_3", "group_5"],
    excludedSampleIds: ["group_7"],
    eventCountPerSample: {             // eligible counts, not raw $TOT
      "group_1": 16942, "group_2": 21289,
      "group_3": 36075, "group_5": 3241,
      "group_7": 180  // excluded: below min_events_for_pooling
    },
    warnings: [
      "group_7 has only 180 eligible events and was excluded from pooled gate fitting. It will still appear in inspection renders and receive gate counts after propagation."
    ]
  }
}

Error: no eligible samples

When zero samples meet min_events_for_pooling, do not fit a gate. Return an error with full diagnostics so the agent can explain the situation and suggest a remedy.

{
  error: "insufficient_events_for_pooling",
  message: "No samples meet the minimum event threshold of 500. Consider lowering min_events_for_pooling or using a single-sample call.",
  poolingDiagnostics: {
    minEventsForPooling: 500,
    includedSampleIds: [],
    excludedSampleIds: ["group_1", "group_2"],
    eventCountPerSample: { "group_1": 180, "group_2": 312 }
  }
}

Warning: exactly one eligible sample

Return the gate, but warn that pooled fitting has degraded to single-sample fitting. The gate coordinates may not generalise.

{
  gate: { /* polygon fit from group_3 only */ },
  poolingDiagnostics: {
    effectiveEventsPerSample: 4200,
    includedSampleIds: ["group_3"],
    excludedSampleIds: ["group_1", "group_2", "group_7"],
    warnings: [
      "Only 1 of 4 samples met min_events_for_pooling. Pooled fitting degraded to single-sample fitting on group_3. Gate coordinates may not generalise across the cohort."
    ]
  }
}

Backward compatibility

When sample_ids is absent and singular sample_id is used, the existing single-sample code path runs unchanged. poolingDiagnostics is absent. No breaking changes.

Documentation line

Balanced pooled fitting uses up to 5,000 events per sample by default. Samples with fewer than 500 eligible events (after any parent gate filter) are excluded from pooling and reported in diagnostics. They still appear in inspection renders and receive final counts after gate propagation.

Feature 3 — suggest_main_cell_gate (new tool)

Naming rationale

The FSC/SSC gate that precedes singlet and apoptosis gating must be called Main cell / non-debris gate. Do not call it:

  • Live-cell gate — live cells and dead cells are both in-scope; this gate only excludes non-cellular debris.
  • Apoptosis removal gate or dead-cell exclusion gate — apoptotic and dead cells are the biology being measured in an apoptosis assay. Excluding them at this stage would bias the downstream Annexin/PI percentages.

The gate should exclude obvious non-cellular events: extreme debris at the bottom-left of FSC/SSC, very large aggregates at the top-right. It should not attempt to separate viable from apoptotic/dead cells based on FSC position.

API

ParameterTypeDefaultDescription
workspace_path string — Path to the workspace JSON file.
sample_id string — Single-sample path. Mutually exclusive with sample_ids.
sample_ids string[] — Pooled path. See Feature 2 contract above.
x string auto X-axis channel. Defaults to the first FSC-A-like parameter found in the sample metadata.
y string auto Y-axis channel. Defaults to the first SSC-A-like parameter.
max_events_per_sample number 5000 See Feature 2.
min_events_for_pooling number 500 See Feature 2. For root-level gate, eligible count is raw $TOT.
mode "non_debris" | "main_population" | "lymphocyte_like" "main_population" Algorithm intent. non_debris: conservative, removes only clear non-cellular events — correct default for apoptosis assays. main_population: fits the dominant scatter cluster. lymphocyte_like: targets the low-FSC, low-to-mid-SSC lymphocyte region. When the calling agent knows the assay type (e.g. apoptosis workflow), it should pass mode: "non_debris" explicitly.
seed number 42 See Feature 2.

{
  gate: {
    type: "polygon",
    name: "Main cells",
    xChannel: "FSC-A",
    yChannel: "SSC-A",
    vertices: [ /* polygon coordinates */ ],
    summary: {
      count: 15453,
      percentOfParent: 91.21
    }
  },
  gateIntent: "non_debris",  // echoes the mode used — agent should surface this to the user
  gateIntentWarning?: "For apoptosis assays this gate is conservative and is not intended to exclude apoptotic/dead cells.",
  poolingDiagnostics?: { /* present when sample_ids used; see Feature 2 */ },
  nextAction: "upsert_gate"  // or "upsert_gates" for multi-sample writes
}

Algorithm notes

Use density-based or HDR-style gating on the FSC/SSC space:

  • Find the highest-density region in the 2D FSC/SSC plot.
  • Draw a conservative polygon around it — err on the side of inclusion. The polygon should capture the dominant non-debris population including cells that have shifted to lower FSC due to early apoptosis.
  • Exclude only clearly non-cellular events: extreme debris below the main cloud (very low FSC and SSC), and very large aggregates/clumps above it.
  • Do not attempt to separate viable from non-viable cells based on FSC intensity; that distinction belongs to the Annexin/PI gates downstream.
Assay context matters

For apoptosis assays specifically, a tight live-cell polygon that excludes low-FSC apoptotic events will artificially reduce the Annexin+/PI+ populations. The main-cell gate should be drawn broadly enough to retain apoptotic cells; they will be characterised downstream by Annexin V and PI staining.

Some assays (e.g. activation assays) do want dead-cell exclusion at this stage. The algorithm should default to conservative/inclusive and let the user tighten the gate manually if the assay requires it.

Apoptosis workflow — full hierarchy

Generic three-level structure that applies across assay types:

Root
  →  Main cell / assay-appropriate morphology gate   FSC-A vs SSC-A   suggest_main_cell_gate
      →  Singlet gate(s)   FSC-A/FSC-H, FSC-A/FSC-W, SSC variants as needed   suggest_singlet_gate
          →  Assay readout gate   Annexin vs PI · live/dead vs marker · tetramer vs marker …   assay-specific tool

For apoptosis specifically:

Root
  →  Non-debris cell gate   FSC-A vs SSC-A   suggest_main_cell_gate(mode: "non_debris")
      →  Singlets   FSC-A vs FSC-H (or user-selected axes)   suggest_singlet_gate
          →  Annexin/PI quadrants (4 gates)   Annexin-A vs PI-A   suggest_apoptosis_quadrants
Critical — apoptosis assay gating

For apoptosis assays, morphology gates should be conservative and assay-aware. They should remove debris/non-events but should not try to purify only healthy/live-looking cells before Annexin/PI quantification. Excluding cells that have shifted to lower FSC due to apoptosis will bias the Annexin+ and PI+ percentages — the most dangerous automated-gating mistake in this assay.

Notes on singlet gating: FSC-A vs FSC-H is most common; FSC-A vs FSC-W and SSC-A vs SSC-H are also used. Some protocols apply singlet gating twice (FSC then SSC). Axis choice is user preference — the tool accepts explicit axes via axes and defaults to FSC-A / FSC-H. Sequential double-gating is deferred; see implementation order.

Pooling rules per gate level

  • Main cell / non-debris gate — pool treatment samples. Exclude the unstained control unless it was collected from the same preparation. Eligible count = raw $TOT.
  • Singlets — pool treatment samples. Eligible count = events surviving the main-cell gate (not raw $TOT).
  • Annexin/PI quadrant thresholds — negative control only. Pooling does not apply. suggest_apoptosis_quadrants already accepts negative_control_sample_id.
  • Final population counts — always per real sample via get_population_table. Pooled fitting is only for gate coordinate derivation.

Implementation order

  • 1
    render_plot / render_plot_image — small_multiples next

    Highest immediate value. Unlocks the inspection step and the “agent catches a distribution shift” demo moment before any gate-fitting changes land.

  • 2
    suggest_main_cell_gate — new tool

    New dedicated tool for the FSC/SSC non-debris gate. Implement with the full pooling contract from day one. Conservative HDR-based algorithm; name the proposed gate "Main cells" by default.

  • 3
    suggest_singlet_gate — add sample_ids pooling + axes parameter

    Extend the existing tool. Add sample_ids pooling (Feature 2 contract). Also add axes?: Array<{x: string, y: string}> to accept explicit axis pairs (default: FSC-A / FSC-H). Sequential double-gating (strategy: "sequential") is deferred — start with single-gate only. Backward compat: single-sample path unchanged.

  • 4
    render_plot / render_plot_image — overlay mode

    Lower priority than small_multiples. Implement after small_multiples is stable.

  • 5
    Physical concatenated FCS export deferred

    Only if users request downstream compatibility with FlowJo or FCSExpress. Not in scope for this spec.
